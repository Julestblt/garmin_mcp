# Activity synchronization

Connection creates a durable `sync_jobs` row and returns immediately. Run `garmin-mcp-worker` separately. It claims one job atomically and fetches one seven-day window, starting with the newest dates. Activity summaries use a range call; new or changed activities receive detail and split calls. Normalized activity and lap/split rows are written under a database connection lock. A lost worker lease can be reclaimed. Replaying a window is safe because `(user_id, provider, provider_activity_id)` is unique and upserts apply provider corrections. The worker skips repeat detail calls when the source update time is unchanged. Imported rows remain after disconnect or reconnect. Only explicit Garmin data deletion removes them.

`GET /v1/connections/garmin/sync` reports state, phase, cursor, oldest synchronized date, the current number of distinct imported activities for this connection, and errors. The worker derives this count from database rows after each window, so replay cannot inflate it. There is no fabricated percentage. The historical floor is set on each sync job.

`POST /v1/connections/garmin/start` accepts an optional `history_start_date` in `YYYY-MM-DD` format. The default is `STRIDE_HISTORY_START_DATE`, falling back to `2000-01-01`. It is stored on the connection's historical sync job. The worker uses the Garmin date-range API in week-sized windows; this bounds each summary fetch, though a very dense week is still accumulated by the upstream library. Route geometry and chart samples are imported by the separate `tracks` job described below, not by these activity windows. Other consumers should use normalized Stride rows rather than live Garmin calls.

Recovery and fitness use separate durable jobs so recent onboarding data arrives while older activities import. Recovery starts at the later of the connection floor and 90 days ago; fitness starts at the later of the connection floor and 365 days ago. Each claim imports one day and saves the next cursor. `provider_observations` stores typed metric values, units, availability, source time, and import time. A present zero is stored as zero; absent fields are `missing` with null values. Current-day values are `partial`. Device support cannot be inferred from an empty Garmin response, so the worker does not label absence as `unsupported`.

Resting heart rate is read from the requested day's `allMetrics.metricsMap.WELLNESS_RESTING_HEART_RATE` entry returned by Garmin's wellness endpoint. Legacy responses with a direct `restingHeartRate` remain supported. A metric for another date never fills the requested day. After deploying this normalization correction, incremental recovery jobs replace previously missing values for the last seven days; older missing observations require replaying their recovery import. This correction does not change historical jobs or delete imported data.

The sync endpoint returns `categories.activities`, `categories.recovery`, `categories.fitness`, and `categories.patterns`. Each category uses `pending`, `running`, `partial`, `complete`, or `failed`; only activities report a verified row count. Patterns are a live weekly aggregate of normalized activities in `provider_training_weeks`, so their completeness follows the activity import. No percentage is reported.

Every normalized write is gated by a compare-and-set on the claimed job: the activity and observation upsert functions lock the `sync_jobs` row and require it to still be `running` with the worker's attempt number and an unexpired lease before writing. The cursor update uses a conditional `PATCH` that returns the updated row, so a worker whose lease expired, or whose job was reclaimed by another worker, cannot overwrite newer state. Such a stale write is discarded without incrementing the failure count, and the reclaiming worker owns the job's progress.

The worker schedules incremental jobs every hour for domains whose historical job succeeded. It revisits the last 14 days of activities and seven days of recovery and fitness, at most once per six hours per connection and domain. Provider corrections upsert into existing rows. Job claims and cursors are persisted, and transient failures use bounded exponential backoff. Run at least one worker container; scheduling is database-idempotent across workers. The onboarding category state tracks historical completion, while the response also includes the latest incremental job and `last_sync_at`. The worker does not stop historical activity import after an empty period because a gap is not proof that older history is absent.

## Activity enrichment

The activity windows now also keep, from data they already fetch, the Garmin activity name (`activity_name`), `calories`, the perceived effort (`workout_rpe`, Garmin's 0-100 value divided by 10, so 1 to 10) and the post-activity feel (`workout_feel`, Garmin's 0-100 value). Missing or zero values are stored as null.

A `tracks` job (mode `incremental`, phase `tracks`) imports one compact track per activity. The hourly scheduler creates it for every connection whose historical activity import succeeded, at most once per hour. Each claim lists up to five activities in the last `STRIDE_TRACK_HISTORY_DAYS` days (default 90, bounded to 1-3650) that have no track, a track built from an older source update, or an `unavailable` track older than one day. It calls Garmin's activity-details endpoint with reduced chart and polyline sizes, normalizes the result in `stride_tracks`, writes it through `upsert_activity_track` under the same job-lease compare-and-set as activities, and requeues itself five seconds later until nothing is pending. Older activities outside the window are left without a track; widen the window to import them gradually.

A track stores, in `provider_activity_tracks` with owner-only read access and cascade deletion with the activity:

- `route`: at most 300 `[latitude, longitude]` points with five decimals, simplified with Ramer-Douglas-Peucker so the shape is kept, plus `bounds`. Treadmill and other indoor activities have no route.
- `series`: aligned arrays of at most 240 points (`elapsed_s`, `distance_m`, `heart_rate`, `speed_mps`, `elevation_m`, `cadence`, `power_w`), averaged inside each bucket. Metrics with no values are omitted.
- `heart_rate_histogram`: seconds spent at each heart rate, measured at full resolution with sample gaps capped at ten seconds, so consumers can compute time in any heart-rate zone definition exactly.
- `status`: `available` or `unavailable`. A single activity that Garmin cannot provide is marked `unavailable` and retried after a day. A rate limit, an authentication error, or a batch where every activity failed requeues the job with backoff and writes nothing.

A track is typically 10-15 KB of JSON. The sync status endpoint and its categories ignore `tracks` jobs, so onboarding progress and the `incremental` summary are unchanged.

Applying the enrichment migration also queues one incremental activity job per connected connection covering the last 90 days, so names, perceived effort and calories are filled for recent history without a full re-import.
